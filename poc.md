Создай минимальный рабочий POC удалённой IDE на Node.js.

## Цель

Система состоит из двух независимо запускаемых компонентов:

1. `core` — standalone backend-процесс на удалённой машине, который предоставляет доступ к файлам workspace и в будущем будет управлять процессами.
2. `desktop` — Electron-приложение, которое подключается к `core` по IP/hostname и порту и предоставляет IDE-подобный интерфейс.

Это должен быть небольшой, но реально запускаемый end-to-end POC. Не добавляй функции, не необходимые для описанного сценария.

## Стек

Используй:

* TypeScript во всём проекте;
* Node.js для backend;
* Electron для desktop-приложения;
* React для renderer-процесса Electron;
* Monaco Editor для редактирования файлов;
* WebSocket для постоянного соединения между frontend и backend;
* npm workspaces или pnpm workspace для monorepo;
* Vite для сборки frontend.

Допустимо использовать небольшую библиотеку для layout/panel management, если она не перегружает POC. Архитектура должна позволять впоследствии:

* создавать несколько панелей;
* размещать в каждой панели набор вкладок;
* перемещать вкладки между панелями;
* добавлять терминал, diff viewer и другие типы вкладок.

Реализовывать drag-and-drop и сложный docking в POC не требуется.

## Структура проекта

Организуй monorepo примерно так:

```text
remote-ide/
  packages/
    core/
    desktop/
    protocol/
  package.json
  README.md
```

`protocol` должен содержать общие TypeScript-типы сообщений и DTO, используемые backend и frontend.

Не смешивай filesystem-логику, WebSocket transport и React UI.

## Backend core

Backend запускается отдельной командой, например:

```bash
npm run core -- --host 0.0.0.0 --port 7331
```

Core должен:

* принимать WebSocket-подключения;
* поддерживать настройку host и port;
* не иметь заранее зафиксированного workspace;
* позволять клиенту открыть workspace, передав абсолютный путь;
* проверить, что путь существует и является директорией;
* хранить workspace отдельно для каждой клиентской сессии;
* возвращать рекурсивное дерево файлов и директорий;
* читать содержимое текстового файла;
* сохранять изменённое содержимое файла;
* возвращать понятные структурированные ошибки;
* логировать подключения, запросы и ошибки.

Все операции после открытия workspace должны принимать относительный путь внутри workspace.

Обязательно защити filesystem API от path traversal: клиент не должен получить доступ к файлам вне выбранного workspace через `..`, абсолютные пути или symbolic links.

Для POC можно считать текстовыми все файлы, которые успешно декодируются как UTF-8. Для бинарного или слишком большого файла возвращай понятную ошибку. Установи разумный лимит, например 2 MB.

Управление shell-процессами и терминалом пока не реализовывай, но оставь для этого отдельный модуль/интерфейс, например `ProcessManager`, с минимальной заглушкой и без неиспользуемой сложной логики.

## Протокол

Сделай небольшой typed request/response protocol поверх WebSocket.

Минимальные запросы:

* `workspace.open`
* `filesystem.listTree`
* `filesystem.readFile`
* `filesystem.writeFile`

Каждый запрос должен содержать:

```ts
{
  id: string;
  type: string;
  payload: unknown;
}
```

Ответ:

```ts
{
  id: string;
  ok: boolean;
  result?: unknown;
  error?: {
    code: string;
    message: string;
  };
}
```

Определи конкретные типы payload/result для каждой операции в package `protocol`.

Поддержи хотя бы следующие error codes:

* `INVALID_REQUEST`
* `WORKSPACE_NOT_FOUND`
* `WORKSPACE_NOT_OPEN`
* `PATH_OUTSIDE_WORKSPACE`
* `FILE_NOT_FOUND`
* `FILE_TOO_LARGE`
* `BINARY_FILE`
* `READ_FAILED`
* `WRITE_FAILED`

## Electron desktop

Electron-приложение должно запускаться как самостоятельное desktop-приложение.

При первом запуске или отсутствии активного подключения покажи connection screen с полями:

* backend host/IP;
* backend port;
* абсолютный путь workspace на backend-машине.

Пример:

```text
Host: 192.168.1.50
Port: 7331
Workspace: /home/user/projects/example
```

После нажатия Connect приложение должно:

1. открыть WebSocket-соединение;
2. отправить `workspace.open`;
3. получить дерево workspace;
4. перейти в основной IDE-интерфейс.

Показывай состояния:

* connecting;
* connected;
* connection failed;
* disconnected;
* workspace error.

Добавь кнопку отключения или возврата к connection screen.

Последние введённые host, port и workspace можно сохранять локально, но не подключайся автоматически без действия пользователя.

## Основной UI

Интерфейс должен напоминать минимальный VS Code layout:

* слева — фиксированная или изменяемая по ширине панель Explorer с деревом файлов;
* справа — основная рабочая область;
* сверху рабочей области — вкладки открытых файлов;
* под вкладками — Monaco Editor;
* между Explorer и рабочей областью должен быть resize divider.

Архитектурно UI должен быть построен вокруг следующих понятий:

```ts
type Panel = {
  id: string;
  type: "explorer" | "editor";
};

type EditorGroup = {
  id: string;
  tabs: EditorTab[];
  activeTabId?: string;
};

type EditorTab = {
  id: string;
  type: "file";
  title: string;
  path: string;
  dirty: boolean;
};
```

Эти типы можно уточнить, но сама модель должна разделять:

* панели layout;
* группы вкладок;
* конкретные вкладки;
* содержимое вкладок.

Не привязывай всё приложение к единственному открытому файлу через набор разрозненных React state-переменных.

## File Explorer

Explorer должен:

* показывать дерево файлов и папок;
* позволять раскрывать и сворачивать директории;
* визуально различать файлы и директории;
* открывать файл по клику;
* повторный клик по уже открытому файлу должен активировать существующую вкладку, а не создавать дубликат;
* показывать кнопку ручного обновления дерева.

Создание, переименование, перемещение и удаление файлов в этот POC не входят.

## Tabs и редактор

Пользователь должен иметь возможность:

* открыть несколько файлов;
* переключаться между вкладками;
* закрывать вкладки;
* редактировать содержимое активного файла;
* видеть dirty indicator у изменённого файла;
* сохранить активный файл через кнопку Save;
* сохранить файл через `Ctrl+S` и `Cmd+S`;
* получить подтверждение перед закрытием dirty-вкладки;
* видеть состояние загрузки и ошибку чтения/сохранения.

При закрытии приложения не требуется сложное восстановление сессии, но нельзя молча потерять несохранённые изменения: покажи стандартное предупреждение, если есть dirty-вкладки.

Определяй язык Monaco по расширению хотя бы для:

* TypeScript;
* JavaScript;
* JSON;
* HTML;
* CSS;
* Markdown;
* Java;
* Python;
* YAML;
* plain text.

## Electron security

Соблюдай базовую Electron security model:

* `contextIsolation: true`;
* `nodeIntegration: false`;
* renderer не должен напрямую использовать Node.js API;
* preload должен предоставлять только минимальный typed API;
* не используй `remote`;
* не отключай web security.

WebSocket-клиент может находиться либо в renderer, либо в main process, но решение должно быть явно обосновано в README. Для POC предпочти наиболее простую архитектуру, не нарушающую Electron security boundaries.

## Ограничения POC

Не реализовывай:

* аутентификацию;
* TLS;
* terminal UI;
* language server;
* Git-интеграцию;
* поиск по проекту;
* extensions/plugins;
* совместное редактирование;
* drag-and-drop docking;
* загрузку файлов целиком в локальную копию;
* file watching;
* несколько одновременно подключённых workspace в одном окне.

При этом явно укажи в README, что backend без аутентификации нельзя выставлять в публичную сеть. Он предназначен только для localhost, доверенной LAN или защищённого туннеля.

## UX и визуальный стиль

Сделай аккуратную тёмную тему без лишнего дизайна:

* компактные вкладки;
* нормальные hover/active states;
* визуальное выделение активного файла;
* читаемые ошибки;
* минимальные отступы, похожие на desktop IDE;
* интерфейс должен занимать всё окно.

Не трать время на логотипы, onboarding и сложную дизайн-систему.

## Команды

В корне проекта должны работать команды:

```bash
npm install
npm run dev:core
npm run dev:desktop
npm run build
npm run typecheck
npm test
```

Если для desktop development требуется отдельная последовательность запуска, подробно опиши её в README.

## Тестирование

Добавь минимальные unit/integration tests для backend:

* открытие существующего workspace;
* ошибка для несуществующего workspace;
* построение дерева файлов;
* чтение файла;
* запись файла;
* блокировка `../`;
* блокировка абсолютного пути;
* блокировка выхода через symlink;
* ошибка при превышении лимита размера.

Не нужно покрывать Electron UI полноценными end-to-end тестами.

## Критерии готовности

POC считается готовым, если можно:

1. Запустить core на одной машине.
2. Запустить Electron desktop отдельно.
3. Ввести IP, port и абсолютный путь workspace.
4. Подключиться к core.
5. Увидеть дерево файлов удалённого workspace.
6. Открыть несколько текстовых файлов во вкладках.
7. Переключаться и закрывать вкладки.
8. Изменить файл в Monaco Editor.
9. Увидеть dirty indicator.
10. Сохранить файл на удалённой машине.
11. Перезапустить чтение файла и убедиться, что изменения сохранились.
12. Изменять ширину Explorer.
13. Получать понятные ошибки при проблемах с соединением или filesystem.
14. Выполнить `npm run build`, `npm run typecheck` и `npm test` без ошибок.
